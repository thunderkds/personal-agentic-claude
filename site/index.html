Easy Kit

A multi-agent supervisor framework: one Supervisor session enforces a 5-stage pipeline through deterministic hooks, not just prompted convention. Install it into any git repo with one command.

  • Pipeline — plan → spawn isolated sub-agents → review → integrate → ship.
  • Claude Code — the Supervisor session and its hooks enforce every stage.
  • Other providers (Codex, Cursor) — Codex reads the full doctrine in AGENTS.md. Cursor gets a thin adapter. See Providers below for what carries over and what doesn't.

View the Supervisor GitHub repository for the source and installation reference.

What you get

Four spawnable sub-agent roles, skills for every pipeline stage, and enforcement hooks that gate merges and spawns — so "write a test first" and "update the board" are checked, not just written down.

Install

Prerequisites: an existing git repo, and git, curl, and a POSIX sh on your PATH. 

curl -fsSL https://raw.githubusercontent.com/thunderkds/personal-agentic-claude/main/setup.sh | sh

Restart Claude Code after install so it picks up the new .claude/agents/, .claude/skills/, and .claude/settings.json.

Installing into an existing project never deletes what is already there: a file or folder the kit would replace is first moved to a backup, listed in the install output. Identical files are left alone.

How backups are named
  • After the kit version it replaces: CLAUDE.md.bak-<commit>, templates.bak-<commit>/, …
  • Today's date, such as CLAUDE.md.bak-20261008, when no earlier version is recorded, as on a first install.
  • A name already taken gets .1, .2, … so no backup is ever overwritten.

The command takes no options — you choose from numbered menus, and Enter takes the default each time:

  • What to do — 1) Install 2) Cancel (or Update / Reinstall / Cancel where Easy Kit is already installed).
  • Which CLIs — 1) Claude Code 2) Codex. Pick one or both (1 2 or 1,2); the ones found on your PATH are pre-selected, and Claude Code when neither is.
  • New or existing project — 1) New project 2) Existing / legacy project. An existing / legacy project gets CLAUDE_LEGACY.md's rules as its CLAUDE.md.

A plan then lists the CLIs, the project type and anything that will be backed up, and asks Proceed? [Y/n] before a single file changes.

  • No terminal (CI, containers) — no menus: the defaults are printed and taken.
  • Anything on the command line — it stops with nothing written.

To pull in newer Easy Kit changes later, run the same command again from your repo root and choose Update (see below).

Update flow

There is one command: run the same install line again inside your installed project (still a git repository). Easy Kit sees it is installed and asks what to do: 

Easy Kit is already installed in /path/to/your-project.
  1) Update (keeps your edits)
  2) Reinstall (backs up your edits)
  3) Cancel
Choose [1]:

Before changing anything it shows a plan — files to ask about, files to remove because the kit no longer ships them, anything to back up — and ends with Proceed? [Y/n].

If the plan lists files you edited, one question about all of them replaces Proceed? [Y/n]: 

How should Update treat your edited files?
  1) Ask me about each one
  2) Overwrite all of them (each backed up first)
  3) Keep all of them
  4) Cancel
Choice [1]:
  • 1 asks about each file, as in the table below. Enter picks it.
  • 2 moves each file to <file>.bak-<commit>, then overwrites it. A file it cannot back up is kept.
  • 3 keeps every edit. 4 changes nothing.
  • Answer n to go back to the menu. Cancel changes nothing.
  • No terminal (CI, containers, ssh without -t) — no menu: it prints the safe default — Update, keeping every edit — and takes it. Reinstall never runs without a terminal.
  • An existing update.sh in a checkout still works: it runs the same Update action.

Update re-fetches the framework fresh, then compares each MANIFEST file — plus CLAUDE.md — against the content hash recorded at the last install/update:

Your copyWhat Update does
Untouched since installSilently overwritten with the latest upstream version
CustomizedShows a diff and prompts per file: overwrite / skip / view diff again. Overwrite first moves yours to <file>.bak-<commit>; skip keeps it
No longer shippedRemoved if you never edited it; kept (and named) if you did
.claude/settings.jsonNot a MANIFEST file, so it is merged rather than copied — on install and on update
How the merge works
  • The kit's hooks are reconciled into it.
  • The kit's permissions.deny entries are appended to yours (add-only); your own permissions and hook entries are kept exactly as they are.
  • The kit's allow or ask rules are never copied.
  • If it cannot be merged — invalid JSON, a symlink, or no python3 — nothing is written, the block to add by hand is printed, and the run exits 2.
Where the hashes are recorded

In .claude/harness-lock.json, which also records the kit's commit ID as kit_commit — the version a .bak-<commit> backup is named after.

Every Update run adds a dated entry to the top of .claude/update-log.md: how your edited files were decided, what happened to each one, and counts for the rest.

An update log entry 
## 2026-10-26 14:05 — Update 75040d9 → b122017
Decided by: auto-approve (overwrite all)
- CLAUDE.md — overwrote (your edits; backup CLAUDE.md.bak-75040d9)
- agents/qa.md — overwrote (your edits; backup agents/qa.md.bak-75040d9)
- 41 kit files you never edited — refreshed
- 2 files added

The log holds paths, outcomes and counts only, never file contents. Older entries stay below, unchanged. Cancel adds no entry.

CLAUDE.md is delivered from the same source the project was installed with — a brownfield/existing project keeps receiving CLAUDE_LEGACY.md's rules, never the greenfield CLAUDE.md — recorded per project in .claude/harness-lock.json.

Which CLIs get updated

Easy Kit stores no list of CLIs. Update asks no CLI question: it refreshes every CLI whose directory is already present. Reinstall shows the CLI menu, pre-selecting those. That means:

  • A Codex-only project refreshes .codex/skills/ and is not given .claude/{skills,agents} it never asked for.
  • A Claude project keeps its .claude/{skills,agents} links repaired — including when a link has gone missing, stale, absolute, or been replaced by a real directory.
  • Adding a CLI later: run the same command, choose Reinstall, and pick the CLI. A CLI already set up that you do not pick is kept and refreshed, and the plan says so — to drop one, delete its folder.

One edge worth knowing: if both .claude/skills and .claude/agents are deleted outright, Update leaves them absent. Restore them: run the command, choose Reinstall, and pick Claude Code.

Why Update leaves them absent

With nothing present, the project is indistinguishable from one that never picked Claude Code.

export GITHUB_USERNAME=your-username
curl -fsSL https://raw.githubusercontent.com/$GITHUB_USERNAME/personal-agentic-claude/main/setup.sh | sh

New vs. existing (brownfield) project — a menu choice in the same curl … | sh line: the menus read your terminal, not the pipe.

  • 2) Existing / legacy project — for an existing codebase. Uses CLAUDE_LEGACY.md, which adds legacy-codebase guidance (risk hotspots, strangler-fig patterns).
  • 1) New project — the default with no terminal. You get CLAUDE.md (only @AGENTS.md) and the full AGENTS.md.

Agent roles

Four roles are directly spawnable via the Agent tool, each scoped to a single TASK_GUIDE. A fifth file, general-agent-template, is not a spawnable role — the shared base template they all inherit.

backend-developer
subagent_type: backend-developer

Core backend engineering role — server-side APIs, services, business logic, and data-access layers, built test-first.

common-infrastructure
subagent_type: common-infrastructure

Environment and shared-config specialist — worktree setup, migrations, shared services; always runs first before implementers start.

frontend-developer
subagent_type: frontend-developer

Core frontend engineering role — UI components, client-side state, interactions, and accessibility, built test-first.

qa-expert
subagent_type: qa-expert

Quality and evaluation role — owns the smoke suite, regression safety, and independent verification of acceptance criteria.

general-agent-template
not directly spawnable — shared base only

Base template inherited by all four roles above. Contains the universal Base Rules, engineering principles, and output requirements that are not restated per role. It has no subagent_type of its own and is never spawned directly.

Hooks

Deterministic shell/python guardrails the harness runs — not the model. Each fires on a PreToolUse, PostToolUse, or Stop event and either blocks the tool call or only advises (prints, never stops execution).

The wiring lives in .claude/settings.json. Both setup.sh and update.sh merge every entry below into that file. No manual merge step.

What the merge keeps

It merges into a .claude/settings.json your project already has too, and keeps your own permissions and hook entries; the only permissions it adds are the kit's permissions.deny entries.

EventMatcherScriptBehavior
PreToolUseAgentpre_agent_validate_guide.pyblocks spawn if the TASK_GUIDE is missing; otherwise only advises (never blocks)
When it advises
  • The spawn prompt has no memory slice or no **Startup reads** block
  • A Depends on task is not Done
  • A task's Demonstration BEFORE is still blank
PreToolUseBashpre_bash_block_unsafe_merge.pyblocks git push/merge if pipeline gates are unsatisfied
PreToolUseEdit|Write|Bashpre_tool_sensitive_path.pyasks you to confirm before a call touches a path listed in .claude/sensitive-paths.txt — unless the active task's guide predicted that exact path
What the list covers

.env*, secrets, production configs, infra.

PreToolUse.*pre_agent_step_limit.pyblocks a task's tool call once it exceeds the step limit (default 90) — self-clearing on the very next call
PostToolUseWritepost_write_register_task.pyadvises — auto-registers new TASK_GUIDE files on the board
PostToolUseAgentpost_agent_move_to_review.pyinert — does not move anything and does not touch any step counter; it only prints a reminder to move the row by hand
Why by hand

The reminder is for the Supervisor. The hand move is deliberate, after two past defects made the automatic move actively harmful.

PostToolUseBashpost_bash_memory_update.pyadvises — prompts a diff-driven memory-update pass after git push/merge/pull
PostToolUse.*post_tool_trace.pyadvises — appends every tool call to memory/event-trace/<task>.jsonl; scripts/verify_trace.py <task> reports whether the trace still matches
How an edit shows

Each line is linked to the one before by a hash chain, with a copy of each line's hash kept outside the repo under ~/.claude/harness-anchors/.

Stop—stop_review_reminder.pyadvises — reminds the Supervisor to run Stage 4 review for pending tasks

Providers

AGENTS.md plus docs/claude-md/ stay the one primary source of truth. Codex reads it directly; Claude Code reads it through the one-line CLAUDE.md import. Cursor gets a thin adapter.

What an adapter carries

The kit's non-negotiable rules (the four Karpathy principle names and the six Hard-Stop Gate titles) inline, pointing back at the primary for everything else.

FileAuto-read byWhat it carries
AGENTS.mdCodex; Claude Code through the CLAUDE.md importThe full doctrine, plus a short section naming what Codex and Cursor cannot enforce
.cursor/rules/agent-base.mdcCursor (alwaysApply: true)Karpathy principle names, Hard-Stop Gate titles, the untrusted-content boundary rule, and the "no TASK_GUIDE = no work" rule, inlined from AGENTS.md

Codex executes the kit's skills directly, by name, from a projected .codex/skills/ directory (choose Codex in the installer's CLI menu) — it is not left with doctrine alone.

  • Each skill's body is capped at 8 KB per Codex's own limit.
  • A skill over the cap is skipped with a named, loud warning rather than truncated.
  • Four of this kit's skills currently exceed it and are skipped for Codex: bugfix, craft-spawn-prompt, diagnose, and write-better-skill.

What a non-Claude provider still cannot enforce: Claude Code's PreToolUse/PostToolUse hooks, the Agent spawn tool, and everything built on them:

  • code-review, security-review, verify, ship, migration-safety, and the git-guardrails hook.
  • Those stay on the Claude supervisor: an adapter carries the doctrine, and Codex can now run the skills it has room for, but the deterministic enforcement layer does not follow.

MCPs

Two separate companion tools, not part of this kit: MCP servers you can run alongside it, each from its own repository.

easy-verifier-mcp

A separate companion tool, not part of this kit: a no-LLM evidence engine you can run alongside Stage 4 review.

  • No LLM and no model API key — ratings are deterministic rules over cited metrics
  • Seven independently callable dimensions, from architecture to blast-radius
  • Auditable coverage — a "found 4/6" always shows the sources it did not find
  • Read-only and local — never runs the target repo's code, no outbound network
  • Kit-aware mode treats this kit's specs, task guides and memory as ground truth

easy-verifier-mcp on GitHub · Easy Verifier site

easy-ui-mcp

A separate companion tool, not part of this kit: a Dockerized MCP server for testing a web UI locally.

  • Playwright browser automation that an agent such as Claude Code drives step by step
  • Returns a JSON and HTML report with screenshots — no server-side LLM, no test scripts to write
  • Separates claims from observations: ui_assert fails the run, ui_check records and continues
  • Captures console errors, page errors and failed network requests as "Browser problems"
  • Version 1 covers web only (Chromium) and runs locally only
