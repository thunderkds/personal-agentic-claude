personal-agentic-claude

A multi-agent supervisor framework for Claude Code. One Supervisor session enforces a 5-stage pipeline (plan → spawn isolated sub-agents → review → integrate → ship) through deterministic hooks, not just prompted convention. Install it into any git repo with one command.

What you get

A base team of four spawnable sub-agent roles, a roster of skills covering every pipeline stage, and a set of enforcement hooks that gate merges and spawns automatically — so "write a test first" and "update the board" are not just written down, they are checked.

Install

Prerequisites: an existing git repo, and git, curl, and a POSIX sh on your PATH. 

curl -fsSL https://raw.githubusercontent.com/thunderkds/personal-agentic-claude/main/setup.sh | sh

Restart Claude Code after install so it picks up the new .claude/agents/, .claude/skills/, and .claude/settings.json.

To pull in newer harness changes later, run the update script from your repo root:

sh update.sh

Update flow

update.sh is a separate script from setup.sh — run it from inside your already-installed project, which must still be a git repository: 

sh /path/to/personal-agentic-claude/update.sh

It re-fetches the framework fresh, then for every MANIFEST file compares your project's current copy against the content hash recorded at the last install/update (.claude/harness-lock.json):

  • Untouched since install — silently overwritten with the latest upstream version.
  • Customized — shown a diff and prompted per file: overwrite / skip / view diff again.

Install variants

Fork install — export your username first and swap it into the URL:

export GITHUB_USERNAME=your-username
curl -fsSL https://raw.githubusercontent.com/$GITHUB_USERNAME/personal-agentic-claude/main/setup.sh | sh

Greenfield vs. brownfield — chosen interactively during setup.sh. Piped installs are non-interactive and default to greenfield (CLAUDE.md). For a brownfield project (an existing codebase), clone this repo somewhere, cd into your target project, invoke that checkout's setup.sh by path, and choose the brownfield option — it uses CLAUDE_LEGACY.md, which adds legacy-codebase guidance (risk hotspots, strangler-fig patterns).

Agent roles

Four roles are directly spawnable via the Agent tool, each scoped to a single TASK_GUIDE. A fifth file, general-agent-template, is not a spawnable role — it is the shared base template every spawnable role inherits Base Rules and engineering principles from.

backend-developer
subagent_type: backend-developer

Core backend engineering role — server-side APIs, services, business logic, and data-access layers, built test-first.

common-infrastructure
subagent_type: common-infrastructure

Environment and shared-config specialist — worktree setup, migrations, shared services; always runs first before implementers start.

frontend-developer
subagent_type: frontend-developer

Core frontend engineering role — UI components, client-side state, interactions, and accessibility, built test-first.

qa-expert
subagent_type: qa-expert

Quality and evaluation role — owns the smoke suite, regression safety, and independent verification of acceptance criteria.

general-agent-template
not directly spawnable — shared base only

Base template inherited by all four roles above. Contains the universal Base Rules, engineering principles, and output requirements that are not restated per role. It has no subagent_type of its own and is never spawned directly.

Hooks

Deterministic shell/python guardrails the harness runs — not the model. Each fires on a PreToolUse, PostToolUse, or Stop event and either blocks the tool call or only advises (prints a message, never stops execution).

EventMatcherScriptBehavior
PreToolUseAgentpre_agent_validate_guide.pyblocks spawn if the TASK_GUIDE is missing
PreToolUseBashpre_bash_block_unsafe_merge.pyblocks git push/merge if pipeline gates are unsatisfied
PreToolUse.*pre_agent_step_limit.pyblocks a task's tool call once it exceeds the step limit (default 90) — self-clearing on the very next call
PostToolUseWritepost_write_register_task.pyadvises — auto-registers new TASK_GUIDE files on the board
PostToolUseAgentpost_agent_move_to_review.pyinert — does not move anything and does not touch any step counter; it only prints a reminder for the Supervisor to move the row by hand (deliberately, after two past defects made the automatic move actively harmful)
PostToolUseBashpost_bash_memory_update.pyadvises — prompts a diff-driven memory-update pass after git push/merge/pull
PostToolUse.*post_tool_trace.pyadvises — appends every tool call to memory/event-trace/<task>.jsonl
Stop—stop_review_reminder.pyadvises — reminds the Supervisor to run Stage 4 review for pending tasks

Packs (optional domain extensions)

The core framework ships four agents for every project. Packs add domain-specific agents and skills on top — selected at install time, never replacing core resources.

PackDomainAgentSkills
mobileFlutter, React Native, Swift, Kotlinmobile-developerui-accessibility, platform-compatibility
dataPipelines, notebooks, ETL, dbtdata-engineernotebook-review, pipeline-safety
devopsTerraform, K8s, CI/CD, Dockerdevops-engineerinfra-safety, deployment-checklist
ai-agentLLM apps, RAG, MCP serversai-engineerprompt-review, eval-design
apiREST/gRPC, OpenAPI, auth flowsapi-designercontract-review, auth-checklist

Install a pack into an existing project — run setup.sh from a persistent local clone (not piped through curl):

sh ~/.supervisor/setup.sh --pack=mobile
sh ~/.supervisor/setup.sh --pack=mobile --pack=api   # multiple packs

Packs still require a persistent local clone at ~/.supervisor (or $SUPERVISOR_PATH) — unlike core resources, packs are not created automatically by a piped install. If bootstrapping a brand-new project and wanting packs on first run, use the sh -c "$(curl ...)" -- --pack=<name> form: 

sh -c "$(curl -fsSL https://raw.githubusercontent.com/thunderkds/personal-agentic-claude/main/setup.sh)" -- --pack=mobile

A plain pipe like curl ... | sh --pack=mobile does not work: sh parses its own flags before it ever reads the piped script, so --pack=mobile is rejected as an unrecognized sh option, not passed through to setup.sh.

Repository layout

The mandatory folder structure created by install. Core resources are copied as real files; project-specific files are created fresh and never overwritten by an update.

PathWhat it contains
.claude/agents/Core sub-agent definitions plus general-agent-template.md
.claude/skills/Custom skills, auto-discovered by Claude Code
tasks/Task guides generated at Stage 2 (per project)
templates/Blank templates for PRD, PROJECT_SPEC, task board, TASK_GUIDE, and more
packs/Optional domain packs — each adds agents + skills for a specific project type
memory/Two-tier hot/cold memory files (per project) — see Memory System below

Memory System

A two-tier hot/cold memory design keeps agents aligned across sessions. Writes are Supervisor-only — sub-agents never write to memory directly.

FileTierHolds
memory/MEMORY.mdHot≤45,000 characters, referenced by path in every sub-agent spawn prompt and read by the agent — not pasted
memory/decisions.mdColdArchitectural and infrastructure decisions
memory/glossary.mdColdCanonical domain terms and core domain models
memory/learnings.mdColdSpec clarifications, patterns, gotchas
memory/codebase-map.mdStructuralDirectory tree, entry points, blast-radius hotspots — generated by map-codebase
