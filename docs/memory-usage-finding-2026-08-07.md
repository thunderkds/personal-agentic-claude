# Is injected memory actually used? — evidence, 2026-08-07 (T063)

**Status of this document**: a measurement, not a decision. It gates T065 (compress vs. shrink vs.
delete `memory/MEMORY.md`). Every number below is regenerated by `scripts/memory_usage_report.py`,
which takes no arguments and writes nothing.

Reproduce:

```bash
# from the main checkout (memory/event-trace/ is gitignored — a worktree has none)
python3 scripts/memory_usage_report.py
# or, from a worktree, pointing at a checkout that has a trace:
CLAUDE_PROJECT_DIR=/path/to/main-checkout python3 scripts/memory_usage_report.py
```

**Headline**: (a) is **established**. (b) is **established** for the current spawn-prompt template
and **not established** for the historical corpus. (c) is **not established** — the trace can show
that a sub-agent *opened* `MEMORY.md`, and it does, in 5 of 5 sessions under the current template;
it cannot show that the agent *drew on* it, and no instrument in this repo can.

---

## 0. Vocabulary — bucket vs. locus

The whole question is an attribution question, so two things that are easy to conflate are kept
apart throughout:

* **bucket** — which `memory/event-trace/<task>.jsonl` a record landed in. Decided by
  `task_context.resolve_task_id`: the active-task pointer file, or a `TASK_GUIDE_Txxx.md` path in a
  path-valued field, or an `Agent` prompt. **It is not decided by who made the call.**
* **locus** — which working copy the record's file paths point at, recovered from the record's
  `summary`. A `/pets/wt-t0NN/` path is a Stage-3 sub-agent's own worktree; the main checkout is
  normally the Supervisor's.

The naive 5-of-49 figure in the task guide conflated the two: it read a *bucket* count as if it were
an *actor* count.

## (a) What does `event-trace` attribute, and to whom? — **ESTABLISHED**

**Answer: both actors, in the same file, separable by time window but not by bucket.**

Two independent lines of evidence.

### a.1 — Direct, first-person (this session)

`memory/event-trace/T063.jsonl` was written live during this task. Its first record is the
Supervisor's `Write` of the guide into the **main checkout** at 13:42:28. Every subsequent record is
this sub-agent's own call against **`/pets/wt-t063/`**, a directory the Supervisor never touched:

```

1 14:19:55 Read   {"file_path": ".../wt-t063/tasks/TASK_GUIDE_T063.md"}                        <- sub-agent
2 14:20:02 Bash   {"command": "mkdir -p .../\.claude/hooks/.state && printf ... active_task"}  <- sub-agent
3 14:20:02 Read   {"file_path": ".../wt-t063/.claude/hooks/post_tool_trace.py"}                <- sub-agent
4 14:20:02 Read   {"file_path": ".../wt-t063/.claude/hooks/lib/task_context.py"}               <- sub-agent
5 14:20:11 Read   {"file_path": ".../wt-t063/.claude/skills/craft-spawn-prompt/SKILL.md"}      <- sub-agent
```

So the trace records **sub-agent tool calls** — settled. Records 3–5 name no guide path, so they are
attributed solely by the state file written in record 2; that detail matters for §(c) below.

### a.2 — Independent reconciliation against T061 spawn telemetry

The `Agent` record for T067 carries the sub-agent's own accounting (`spawn.tool_stats`, added by
T061). Comparing it against the T067 bucket **within the sub-agent's session window**, plus the
`_untagged` records in the same window:

```
bucket T067   session window 2026-08-07T10:18:56 .. 2026-08-07T10:27:10
  bucket records excluded as pre-session (Supervisor's own): 1
  read       agent-reported=4    in-window bucket=1    +untagged=3    => 4    EXACT
  bash       agent-reported=14   in-window bucket=12   +untagged=2    => 14   EXACT
  edit_like  agent-reported=15   in-window bucket=14   +untagged=0    => 14   residual -1
  total      agent-reported=33   in-window bucket=27   +untagged=5    => 32   residual -1
```

32 of the sub-agent's 33 self-reported tool uses are located in the trace: 27 in its own bucket, 5
in `_untagged`. Reads and Bash reconcile exactly. One edit-like call is unaccounted for (3% of the
session); its cause is **not established** and it does not bear on the attribution conclusion.

> **A near-miss worth recording.** The first cut of this analysis windowed only the `_untagged`
> side and got `edit_like 15 == 15` and `total 33 == 33` — a perfect reconciliation that was
> **wrong**. The unwindowed bucket still contained the Supervisor's pre-spawn guide `Write`, which
> silently compensated for the one missing agent edit. Two errors cancelling produced a more
> confident-looking answer than the truth. The published numbers are the windowed ones.

### a.3 — Consequence: why 5-of-49 measures nothing

A sub-agent's mandatory-startup reads happen **before** it arms the active-task pointer — the
`craft-spawn-prompt` element-6 instruction says to arm it "before running any test or verification
command", which is after reading the guide, `PROJECT_SPEC.md`, the agent guide, and `MEMORY.md`.
Those reads therefore land in `_untagged`, not in the task bucket. Confirmed on T067: its `MEMORY.md`
read at 10:19:08 is in `_untagged.jsonl`, while its guide read at 10:18:59 is in `T067.jsonl`.

That is exactly the systematic bias the naive count suffered:

```
task buckets with >=1 Read of MEMORY.md: 6 of 61      <- the untrustworthy figure
_untagged Reads of MEMORY.md: 30                       <- where they actually go
```

The naive figure is not a low measurement of memory use. It is a measurement of **when agents arm
the trace pointer**, which is a different variable.

### AC2 — what could not be settled from existing records

Two things, both named rather than guessed:

1. **The 1-call residual** in a.2. Would be settled by one further spawn with `tool_stats` captured;
   only 2 records in the whole corpus carry it (T061 shipped today), so `n=1` for real work.
2. **Actor attribution for `Bash` records that name no path.** Locus is silent for those, and
   `task_context.py` deliberately never scans `Bash` command text. Time-windowing works only when a
   spawn record with telemetry brackets the session. **Smallest experiment that would settle it
   generally**: have `post_tool_trace.py` record the harness's own agent/session identifier
   alongside the task ID — a one-field hook change, no new spawns, no cost. That is a follow-up
   task, deliberately out of scope here.

## (b) Does `MEMORY.md` reach a sub-agent verbatim, or as a path? — **ESTABLISHED (current template)**

`craft-spawn-prompt` element 4 mandates: *"Memory injection | Full contents of `memory/MEMORY.md`,
verbatim"*. `CLAUDE.md` and `MEMORY.md`'s own header both restate it ("Injected in full into every
sub-agent spawn prompt").

**What actually happens is the path channel, not the verbatim channel.**

```
Agent records: 48 (with T061 spawn telemetry: 2; summary truncated at 300 chars: 47)
openings naming memory/MEMORY.md as a PATH to read: 4 ['T053', 'T055', 'T056']
openings containing MEMORY.md VERBATIM (its own H1): 0 []
```

Three real spawn prompts recovered from `event-trace`, quoted from their `summary` fields:

* **T053** — `"... along with .claude/agents/common-infrastructure.md, PROJECT_SPEC.md, memory/MEMORY.md (read it in full — it is your project m..."`
* **T055** — `"... along with .claude/agents/common-infrastructure.md, PROJECT_SPEC.md, memory/MEMORY.md (read it in full — it is your projec..."`
* **T056** — `"... along with .claude/agents/common-infrastructure.md, PROJECT_SPEC.md, memory/MEMORY.md (read in full), and .claude/hooks/l..."`

An instruction to *read a file in full* is incoherent if its contents are already pasted above. And
a fourth, decisive because it is complete rather than truncated: **this task's own spawn prompt**,
received first-person by the agent writing this document, contains no `MEMORY.md` content. It says
`Also read memory/MEMORY.md`.

Corroborated behaviourally: sub-agents in the five sessions run under the current template each
performed exactly one `Read` of `<their own worktree>/memory/MEMORY.md`. An agent handed 200 lines
verbatim has no reason to open the file.

### Limits of this claim

`summary` is capped at `MAX_SUMMARY_LEN = 300`, so for the 47 truncated `Agent` records this can only
inspect the opening. **A verbatim paste later in a prompt cannot be ruled out from the trace**, and
the zero above must be read as "no verbatim paste visible in any recovered opening", not "no
verbatim paste ever occurred". The claim is firm for the four prompts where the memory reference is
visible, and firm for T063 where the whole prompt is known.

Token telemetry does not settle it either: T067's spawn shows `cache_read_input_tokens: 81781`
against a no-op probe spawn's `15294`, but that is cumulative across the session, so a ~10,700-token
paste cannot be isolated within it. Recorded as **not decisive**, not as evidence either way.

### AC4 — divergence between mandate and practice (a finding, not fixed here)

| What | Where |
|---|---|
| `craft-spawn-prompt` element 4 mandates the full contents of `MEMORY.md`, verbatim | `.claude/skills/craft-spawn-prompt/SKILL.md` line 33 |
| Practice: a path reference, sometimes with "read it in full" | **T053, T055, T056** (visible in prompt openings); **T063** (complete prompt, first-person) |
| Practice: no memory reference at all in the prompt opening | 44 further `Agent` records, T018–T061 — but truncation means "not visible", not "absent" |

Affected task IDs where divergence is **directly evidenced**: **T053, T055, T056, T063**.

This is reported, not fixed — `craft-spawn-prompt` is on this task's Must-Not-Touch list. Note the
divergence is not obviously the wrong behaviour: the path channel costs ~20 tokens instead of
~10,700 and, per §(c), the agents do open the file. Which channel *should* be canonical is a T065
decision.

## (c) Is there an observable sign that a sub-agent draws on it? — **NOT ESTABLISHED**

### Operational definition of "used" (AC5)

Three progressively stronger senses, and what this repo can observe of each:

| Sense of "used" | Observable here? |
|---|---|
| **U1 — delivered**: the content reached the agent's context | Yes. Verbatim paste is inspectable in the prompt (§b); a `Read` record proves delivery-by-path. |
| **U2 — opened**: the agent spent a tool call fetching it | Yes — a `Read` record whose locus is the agent's own worktree. |
| **U3 — drawn upon**: the agent's output was different because of it | **No.** No instrument in this repo observes it. |

U3 is unobservable because `post_tool_trace.py` stores only `timestamp`, `tool_name`, a 300-char
`summary` of the **input**, `is_error`, and (for `Agent`) spawn cost fields. **Agent output text is
never recorded** — `tool_response` is read only for `is_error` and the T061 cost fields, and
`task_context.py` documents "`tool_response` is never read" as a deliberate attribution rule. There
is therefore no corpus in which a citation of memory could be searched for.

### What the evidence does show (U2)

```
worktree:t059  records=29   MEMORY.md reads=1
worktree:t060  records=45   MEMORY.md reads=1
worktree:t061  records=50   MEMORY.md reads=1
worktree:t063  records=28   MEMORY.md reads=1
worktree:t067  records=37   MEMORY.md reads=1
worktrees with >=1 MEMORY.md read: 5 of 32
```

**5 of 5** sub-agent sessions run on 2026-08-07 under the current spawn-prompt template opened
`MEMORY.md`, exactly once each. **0 of 27** earlier worktree sessions did.

That discontinuity is sharp and dated, and it is tempting to read as "the new template works". It
should not be read that way without qualification, because of a genuine counter-observation:
**T054, T055, T056 and T057 (2026-08-06) had prompts that explicitly said `memory/MEMORY.md (read it
in full)` and show zero reads** across 56, 13, 46 and 41 records. Either those agents did not comply,
or they read it via a main-checkout path that locus cannot distinguish from the Supervisor's own 43
main-checkout reads. **Not established which.**

### The prompt/memory confound (explicitly unresolved)

Even at U3, a behavioural measure would not be clean. Spawn prompts this session **restate memory
content inline** — T059's, T067's and T063's each warn that `git checkout` is guardrail-blocked,
which is itself a recorded memory learning. An agent that avoids `git checkout` may be obeying the
prompt. Any behavioural claim about memory would need the two channels separated (a spawn whose
prompt restates nothing that `MEMORY.md` contains), which no existing record provides. **Labelled as
unable to separate**, per AC6.

### Further limits, stated rather than buried (AC5)

* **Memory that silently prevents a mistake leaves no trace at all.** The mistake that does not
  happen produces no record, in any instrument, ever. This is the single largest limit on the whole
  question and it is not fixable by better instrumentation.
* This document's author read `memory/MEMORY.md` as a mandatory startup step, which contributes the
  `worktree:t063 reads=1` row above. That data point is **contaminated by self-measurement** and
  should be discounted; the 2026-08-07 pattern holds at 4 of 4 without it.
* The 43 main-checkout `MEMORY.md` reads are a mix of Supervisor memory-pass work and sub-agents that
  worked in the main checkout ("no worktree needed"). Not separable. Not counted as agent use.

### AC6 — what this does NOT say

This document does **not** conclude that memory is unused. No citation evidence exists in either
direction, because no instrument captures agent output. Absence of a citation is not evidence of
non-use. The honest verdict on U3 is **not established**.

**Smallest experiment that would settle U3**, offered for approval rather than run (cost estimate:
2 spawns, ~85k tokens each ≈ one T067-sized task): two spawns on one small identical task, prompts
identical and restating no memory content, one with `MEMORY.md` reachable and one without, comparing
whether the memory-less arm makes a mistake `MEMORY.md` records the fix for. This is the A/B the
guide put out of scope, named here so the decision is the Supervisor's.

## (d) Implication for T065 (AC7)

**Recommendation: shrink the hot tier. Do not compress. Do not delete. Decide the channel first.**

Reasoning, in the order the evidence supports it:

1. **Deletion is not supported.** It would require evidence of non-use, and there is none — U3 is
   not established (§c, AC6). Deleting on this evidence would repeat DDR-0002 exactly: acting on an
   instrument that never captured the metric.
2. **Compression as originally framed is close to pointless, for a reason nobody predicted.** The
   premise was ~10,700 tokens injected verbatim into every spawn. That is **not what happens** (§b):
   the current prompts pass a *path*, costing ~20 tokens. There is no 10,700-token-per-spawn bill to
   compress away. Whatever the file costs, it costs once per agent that chooses to open it — and
   what it costs then is a `Read` of the whole file either way, which compression *would* reduce.
3. **So the real T065 decision is a channel decision, and it comes first**: should element 4's
   verbatim mandate be honoured (making size expensive per spawn, and compression valuable), or
   should it be amended to match the path practice already in use (making size cheap, and the
   200-line cap the only thing worth tuning)? The mandate and the practice currently disagree, and
   T065 cannot be scoped until one of them is chosen. Recommend amending the mandate to the path
   channel: it is ~500x cheaper per spawn, it is what 4 of 4 evidenced prompts already do, and 5 of
   5 agents under it did open the file.
4. **Shrinking the hot tier is safe under either branch** and independently justified: at 200 lines
   the file is at its own documented cap, and every agent that opens it pays for all 200 lines to
   learn the handful relevant to its task.
5. **Blocking dependency**: none of the above needs U3 settled. If the Supervisor wants U3 settled
   anyway, run the A/B in §c before T065; otherwise T065 may proceed on the channel decision alone.

## Instrument defects found (findings, not fixed here)

1. **The active-task pointer is armed too late to capture startup reads** — `craft-spawn-prompt`
   element 6 says "before running any test or verification command", which is after the mandatory
   startup reads. Every agent's `MEMORY.md`/`PROJECT_SPEC.md`/agent-guide read therefore lands in
   `_untagged`. Moving the instruction to "as your first action" would fix per-task attribution of
   exactly the reads this question is about. (Touching that skill is out of scope here.)
2. **The trace carries no actor field** — see AC2 above. One hook field would remove the need for
   the locus heuristic entirely.
3. **`MAX_SUMMARY_LEN = 300` prevents any prompt-content audit** — §b could only inspect openings.
   Noted, not worked around.
